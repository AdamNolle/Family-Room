# Implemented architecture

## Boundaries

`crates/family-core` owns catalog persistence, signed operations, grants, encryption, originals, source adapters and transfer jobs. Swift/Kotlin clients call UniFFI `FamilyCore.open(directory, recoveryKey)` and `command(json)`. Windows uses a bounded handle-based C ABI with scalar word access, not shared ownership of Rust pointers. Linux calls the same Rust engine directly.

UniFFI supplies official Swift/Kotlin bindings; packaging native libraries is a separate build responsibility. [UniFFI documentation](https://mozilla.github.io/uniffi-rs/latest/) explains that boundary. UI rendering, Photos permissions, key storage and AVFoundation rendering remain native responsibilities.

Shared media records keep `contributed_at` separate from `captured_at`; the signed operation preserves when a Room received an item even when its original date is older. Legacy records default to an unknown contribution time and stay out of recency digests.

The v1 local catalog is encrypted JSON with an exclusive file lock and atomic replacement. This avoids Apple-only persistence but is not a database or a scalable catalog/index implementation. Schema versions reject unsupported or corrupted inputs instead of replacing them. Optional device cache limits are encrypted local catalog state keyed by Room, never included in Room operations. Sync-triggered cleanup re-downloads and authenticates another replica before removing local encrypted originals; offline pins, damaged originals, and sole copies are never eligible. A production indexed catalog/migration strategy remains open. Readable exports include an explicit original-name/export-path mapping. Export filenames replace reserved characters, bound UTF-8 length, preserve ordinary extensions and prefix the scoped content ID to avoid collisions and reserved device names; see [Windows filename rules](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

Near-duplicate photo review stores a difference hash per imported supported photo in the encrypted device-local catalog; hashes never enter Room operations or packets. On-demand backfill decrypts local originals into a size-bounded in-memory buffer, verifies the original hash, then decodes JPEG, PNG, TIFF, or WebP under dimension/pixel limits. HEIC/HEIF/AVIF/DNG/GIF and oversized or unavailable originals are skipped and counted. Candidate generation and result counts are bounded; suggestions are review-only, and neither originals nor album membership are changed. Similarity is a visual heuristic, not identity or duplicate proof.

Video finding stores timestamped evidence in the encrypted device-local catalog. Observations use `speech`, `sound_event`, `screen_text`, or `visual_label` modalities. Search filters scope audio to speech and sound events and frames to OCR and visual labels. An exact phrase result requires ordered words in one speech-transcript or OCR text stream; it describes recognized text, not guaranteed recognition accuracy. Sound and scene-model labels remain suggestions at every confidence. Retrieval normalizes common inflections and a conservative concept vocabulary (for example, audience/applause/clapping and laugh/giggle) to find likely moments, including one-term sound clues. These aliases affect suggestions only: quoted searches still require the original ordered words, and aliases never turn classifier output into exact evidence. This is local lexical/concept retrieval, not general embedding-based semantic search. Apple analyzes video frames with AVFoundation/Vision and speech with on-device Speech; it also uses Sound Analysis for timestamped environmental-sound suggestions. Android uses ML Kit and optional pinned English Vosk speech. Windows/Linux use the Rust `family-video-indexer` helper with FFmpeg/FFprobe, Tesseract, optional whisper.cpp, and an optional loopback-only visual model. All media and analysis stay on-device; indexes never enter the Room sync journal. The four platforms do not yet have parity for environmental sound classification, model installation UX, general embedding search, speaker/face identity, or measured family-library accuracy. See [video search and indexing](VIDEO_SEARCH.md).

Quoted video searches retain unquoted words as soft context hints. An ordered phrase remains exact only when it appears in one speech-transcript or OCR stream; nearby audio/frame observations can improve ranking and appear as separate context evidence without identifying who is speaking. Classifier labels remain suggestions, and cached and fallback search return the same evidence contract.

Moment suggestions are computed locally when requested, using capture timestamps from undeleted photos and videos. The read-only command groups at least three unassigned assets separated by no more than three hours, with a maximum cluster span of twelve hours. It does not infer calendar dates or event names. Apple and Android Home let contributors review candidates, adjust the title and asset selection, and call `save_moment` only after an explicit save. Windows and Linux review surfaces remain open. Apple Keychain, Android Keystore, Windows DPAPI and Linux Secret Service protect the device recovery secret in production clients. Android stores its random catalog key wrapped by Android Keystore and reveals the hex recovery key only after an explicit request; the recovery UI uses system document providers with the core encrypted-backup format. macOS Debug builds deliberately use a separate development vault and an owner-only local recovery-key file, excluded from encrypted backups. That development-only implementation is compiled out of Release builds. It avoids rebuilding-app Keychain authorization and preserves the pre-existing production vault without reading or replacing its key. A local file has less protection than the production credential stores. A full backup contains encrypted identity, catalog, original blobs and organization. Losing both secret and backup loses access; an invitation is not a backup.

Timeline clip times are explicit: start and fades use output seconds; trim-in, duration and keyframe positions use source seconds, with playback speed converting between them. Split clips preserve interpolated endpoint keyframes and store fade-in/fade-out offsets in output seconds, so neither picture nor sound restarts its envelope at a cut. Older clips default these offsets to zero. Audio rendering combines keyframed gain with both fades before creating adaptive native ramps; it does not overwrite keyframe ramps with fade ramps. The native export tests compare decoded before/after split frames and audio, while all-platform rendering and formal timeline-schema negotiation remain release gates.

## Encryption and identity

Metadata uses XChaCha20-Poly1305 with context-bound associated data. Originals use a versioned FRB1 stream: original length and independently authenticated 1 MiB chunks, random nonces, Room/asset/chunk context. Materialization verifies the original SHA-256 before atomically exposing a file. Room-specific HMAC identities prevent raw content hashes from being global public identifiers. Ed25519 device keys sign grants and catalog operations.

Room secrets and provider tokens are stored only inside the encrypted local catalog. Shared encrypted packets exclude source credentials and local watch state. Decrypted media used for native previews/rendering is held in a per-run private cache and removed on normal teardown; crash cleanup and comprehensive memory/cache hardening remain open.

Current grants are owner-signed and device-bound. Admin/contributor/viewer permissions are checked by the core and gateway. Ordinary Room grants cover that Room’s media and metadata. Album-only publication creates an independent catalog scope, secret and re-encrypted originals; its viewer invitation contains no parent Room key, provider credentials or unrelated operations. Publishing again updates captions, dates, linked components and membership; the parent originals remain intact. This is explicit publication rather than continuous restricted-album collaboration. Previously published ciphertext and downloaded copies cannot be withdrawn. Device revocation and owner succession rotate keys for new media and catalogs, with signed access revisions and recipient-sealed key bundles. Ownership offers are signed by the outgoing owner, bound to the accepting device and revision, then accepted in a successor-signed access change. Core and gateway reject competing policy branches. Newly connected gateways are initialized with the complete signed access history so the original owner remains the trust anchor. Previously accepted operation hashes preserve history; invalidated offline edits and their local originals remain recoverable in encrypted backups. See [the access protocol](ACCESS_PROTOCOL.md) for offline semantics and limits. Trusted-device pairing and independent cryptographic review remain release gates.

## Sync

Each Room has a signed append-only operation journal. Operations carry protocol version, unique ID, author, owner-signed grant, logical clock, entity, kind and value. Import merges reject invalid signatures, mismatched scope/author and edits to immutable original metadata. Replays are idempotent. Different fields converge using deterministic ordering; caption history and immutable project revisions preserve conflicting values. Albums use per-item membership registers so independent offline additions/removals survive concurrent metadata changes. Concurrent ordering/title edits still use deterministic last-writer ordering. Multiple offline imports of the same Room-scoped content identity use the first creation in canonical journal order; later duplicate creations cannot reset caption/favorite/date edits.

Sources store encrypted per-device journals and opaque encrypted media. Fetch prefers a local original, then configured sources. Nearby peer preference/discovery is not implemented. Private film drafts remain local; publication explicitly enters the shared journal.

The core persists transfer progress and resumable upload-session state. Local/mounted sources resume verified chunks across engine restarts. Google Drive/OneDrive upload session code exists but needs live-provider tests. WebDAV and gateway capabilities report non-resumable uploads. Cancellation takes effect between core transfer steps; a blocking network request may delay it.

Automatic folder rules store destination Room, pause, exclusions, history choice and acknowledged source fingerprints. Apple Photos stores baselines/acknowledged resource IDs and preserves resource components. A Photos batch rechecks the current rule, destination, pause, contribution permission and exclusions inside the core, then commits linked originals and the source checkpoint together; a failed batch does not advance the checkpoint. Polling occurs while the app is active. It does not promise continuous mobile background availability. OS-managed execution is still needed: [Apple background networking](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background), [Android transfer options](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options).

## Providers and gateway

The S3-compatible adapter signs requests with SigV4 and the actual ciphertext payload hash. It supports path-style bucket/prefix and explicitly configured virtual-hosted endpoints, temporary credentials, paginated listing, and persisted 8 MiB multipart uploads. Completion checks HTTP status and XML; verified copies require downloading, authenticating every encrypted chunk and checking the original SHA-256 and byte length. Verification streams to a sink without retaining a plaintext original. Detected damage survives a failed command rollback, so failed recovery cannot restore a false verification claim. Cancellation aborts unfinished parts, or records pending cleanup when disconnected. S3 quota is unknown. Live AWS/MinIO interoperability remains unverified. See [AWS signing](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html) and [multipart completion](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).

Adapters declare quota, sharing, resume, delegated access and background capabilities. Local uses a real directory. WebDAV uses approved server credentials. Drive uses a visible app-owned folder, not hidden appDataFolder, which cannot share files. [Google’s constraints](https://developers.google.com/workspace/drive/api/guides/appdata) explain why. OneDrive uses app-root storage with access owned by the connected account. Tokens are manually supplied development configuration; OAuth consent, refresh and reauthorization flows are unfinished. No free-plan quota is hardcoded.

The optional `family-gateway` listens on loopback by default. Put TLS in front for remote use. It stores ciphertext on disk or proxies through an operator-configured source. It receives signed requests containing method/path/body hash/timestamp and a device-bound grant. Room prefixes and writer-owned journal names are enforced; viewers may publish their own permitted metadata journal but cannot write original blobs. The gateway never receives a Room key.

Start a local gateway with:
```sh
cargo run -p family-core --features gateway --bin family-gateway -- /path/to/ciphertext
```
See `gateway_main.rs` for optional arguments/environment. Operator provider configuration must have private Unix permissions. Gateway registration authenticates an Owner grant and stores the complete signed access history, including the original owner trust anchor after succession. Replay nonce tracking, abuse protection, quota administration, gateway upload resume and deployment operations remain open.

## Projects

The portable StoryProject declares `format_version: 1` and serializes dimensions, asset IDs, layers, start/trim/duration/speed, volume/opacity/exposure/saturation, titles, fades, keyframes, chapters and immutable revision IDs. Legacy unversioned projects use format 1. Unsupported versions are rejected before editing/rendering or rewriting a local catalog. Timeline validation bounds sizes, times, tracks and values before native UI/rendering. `create_story` durably creates a private draft; `split_story_clip` derives a validated edit without publishing or saving a revision. Both Apple and Android editors use the shared split command. See [the timeline contract](TIMELINE_FORMAT.md). Assets stay unchanged. Apple renders through AVFoundation and Core Image, with chapters exported as a sidecar. Android renders on device through Media3 1.11.1 with timed visual layers, original clipping, pitch-preserving speed, titles, linear RGB adjustments, opacity automation/fades and per-sample audio gain before native mixing/encoding. Inputs and preview movies stay in the app cache; only explicit publication imports the encoded movie into the encrypted Room. Unsupported formats or trims beyond the source are rejected. Windows/Linux renderers, subtitles, editor leases, detailed grading and equivalent output across all platforms are unfinished. See [Media3 composition](https://developer.android.com/media/media3/transformer/composition) and [compositor settings](https://developer.android.com/media/media3/transformer/videocompositorsettings).

## Explicit storage overflow

Each device keeps one preferred and at most one explicitly chosen overflow source per Room in its encrypted local catalog. Source preferences and provider tokens are not exported in Room packets. `sync_all` synchronizes enabled alternate sources before the preferred source; if the preferred encrypted catalog update or media transfer reports capacity exhaustion, it may attempt the selected overflow source only when it is in the same Room, enabled, and its own catalog sync succeeded. Apple active-app uploads apply the same decision while stepping resumable transfers. Paused or unselected sources are never used for automatic overflow. A successful fallback retains the preferred job's waiting state and the verified overflow replica; originals stay in the local vault. Provider-reported quotas and configured budgets are distinct inputs. Live cloud quota exhaustion and mobile background execution still require platform validation.


Apple face review uses Vision only after explicit member action. Android uses a bundled ML Kit face detector only after a member opens People → Review face crops; it scans photo originals already saved in that Room on this device and does not download a model at runtime. Both clients create temporary crops for review and discard them when the sheet closes. The member manually selects or creates a Person before the app adds that Person ID to the whole photo; the tag is encrypted and shared as Room metadata. Neither client generates or persists face embeddings, assigns identities, or groups faces across photos. Background recognition and Windows/Linux face review remain unimplemented.

## Room departure

`leave_room` is a local-device departure. It rejects the active Room owner until a successor accepts ownership, then removes the Room catalog entry and active Room keys from this device, clears that Room's storage credentials, upload rules, queued transfers, replica records and local video index, and invalidates the in-memory video-search cache. Encrypted original files may remain in the device vault and an older device backup may restore the Room. Local departure does not create an owner-signed access revision or remove the device from the shared member roster; an owner must separately revoke the device to rotate Room keys and remove its grant across the Room. Native clients state this distinction before confirming.
